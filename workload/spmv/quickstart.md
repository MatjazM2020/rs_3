# SpMV (Sparse Matrix-Vector Multiplication) Kernel Benchmark - Quickstart Guide

## Overview

This project benchmarks the performance of four Sparse Matrix-Vector Multiplication (SpMV) kernels implemented using RISC-V Vector Extension (RVV) intrinsics on the GEM5 simulator. The benchmark evaluates how different memory access patterns (unit-stride, strided, and gather operations) impact performance across varying vector lengths and cache sizes.

### Kernels Tested

1. **Unit-stride** (k1): Loads `val[]`, `x[]`, and `y[]` sequentially
   - All accesses are contiguous in memory
   - Maximizes cache efficiency
   - Expected: Best performance, lowest CPI

2. **Strided** (k2): Loads `x[]` with fixed stride of 8 elements
   - Introduces gaps in memory access pattern
   - Tests prefetcher behavior with strided access
   - Expected: Medium performance

3. **Gather (sorted)** (k3): Loads `x[col[j]]` using sorted column indices
   - Access order is monotonically increasing
   - Hardware prefetcher can partially anticipate future accesses
   - Expected: Worse performance than strided

4. **Gather (random)** (k4): Loads `x[col[j]]` with randomly shuffled indices
   - Access order is unpredictable
   - Defeats the hardware prefetcher
   - Expected: Worst performance, highest CPI

## Experimental Configuration

### Parameters Tested

- **Vector Lengths (VLEN)**: 256, 512, 1024 bits
- **L1 Cache Sizes**: 8 KiB, 64 KiB
- **Scalar CPU**: O3 (out-of-order, with default settings)
- **Clock Frequency**: 3 GHz
- **Memory**: 7 GiB DDR3-1600

### Total Test Combinations

- 3 VLEN values × 2 L1 cache sizes × 4 kernels = **24 simulations**
- Estimated execution time: **~24 hours**

## Understanding the Results

### ANALYSIS.md Report

The analysis report is automatically generated by `aggregate_results.py` after all simulations complete. It includes:

- **Summary tables** organized by kernel, showing CPI and L1 cache metrics
- **Detailed analysis** by L1 cache size and VLEN
- **Key observations** highlighting best/worst performers
- **Performance patterns** for each kernel type

The `detailed_metrics.csv` file can be imported into spreadsheet applications for custom analysis:

## Running Individual Tests

To run a single test configuration manually:

```bash
# Set up GEM5 paths
GEM5_WORKSPACE=/d/hpc/projects/FRI/GEM5/gem5_workspace
GEM5_PATH=$GEM5_WORKSPACE/gem5/build/RISCV_ALL_RUBY

# Compile the binary locally
make clean && make

# Run a specific test (e.g., VLEN=256, L1=8KiB, unit-stride kernel)
srun apptainer exec $GEM5_WORKSPACE/gem5_rv.sif \
    $GEM5_PATH/gem5.opt --outdir=results_test \
    cpu_benchmark.py --vlen=256 --l1-size=8KiB --kernel=1
```

### Python Script Parameters

The `cpu_benchmark.py` script accepts:

- `--vlen=VALUE`: Vector length in bits (e.g., 256, 512, 1024)
- `--l1-size=SIZE`: L1 cache size (e.g., 8KiB, 64KiB)
- `--kernel=ID`: Kernel to run
  - 0 or omitted: Run all 4 kernels
  - 1: Unit-stride only
  - 2: Strided only
  - 3: Gather sorted only
  - 4: Gather random only

Example:
```bash
./gem5.opt cpu_benchmark.py --vlen=512 --l1-size=64KiB --kernel=2
```

## Expected Performance Patterns

### By Kernel Type

- **Unit-stride (k1)**: Lowest CPI (~1-2), highest cache hit rate
- **Strided (k2)**: Medium CPI (~2-5), good cache behavior
- **Gather sorted (k3)**: Higher CPI (~5-10), reduced hit rate
- **Gather random (k4)**: Highest CPI (~10-20+), lowest hit rate

### By Vector Length

- Larger VLEN may improve performance for vectorizable kernels
- Cache effects become more pronounced at larger VLEN

### By L1 Cache Size

- 64 KiB should outperform 8 KiB for all kernels
- Impact is most significant for gather patterns (higher miss rates)
